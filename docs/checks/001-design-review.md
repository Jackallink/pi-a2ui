## Initial finding P1-01 (resolved by design amendment): Pi dispatch is asynchronous behind a void extension API

The current contract and AC-03 promise that an accepted browser action continues the conversation and characterize unavailable delivery as an HTTP error. The pinned Pi public extension method returns `void`, but its runtime implementation calls asynchronous `AgentSession.sendUserMessage(...).catch(...)`, reports failures through Pi's extension error machinery, and returns immediately. The underlying prompt path can await input handlers and authentication before queueing/starting a turn. A synchronous callback double which throws does not establish detection of these real failures. For example, a valid action with no usable model credentials can receive 202 and consume its deduplication ID while Pi later reports an error and starts no turn.

Evidence: [Pi v1.5.0 extension types](https://raw.githubusercontent.com/earendil-works/pi/v1.5.0/packages/coding-agent/src/core/extensions/types.ts), `ExtensionAPI.sendUserMessage`; [Pi v1.5.0 session implementation](https://raw.githubusercontent.com/earendil-works/pi/v1.5.0/packages/coding-agent/src/core/agent-session.ts), `_bindExtensionCore`, `sendUserMessage`, and `prompt` (also independently downloaded into `/tmp/pi-a2ui-design-review/pi-agent-session.ts`).

Required amendment: explicitly define HTTP 202 as a validated, deduplicated **single bridge dispatch attempt**, not Pi admission, turn creation, or model success. Use a browser label such as “Sent to Pi”; explain asynchronous failures are reported in Pi and an ambiguous outcome must not trigger automatic retries. Set `expandPromptTemplates:false` explicitly. Keep synchronous exception handling, but do not claim it catches Pi's asynchronous rejection. AC-03 and walkthrough/plan oracles must assert one bridge invocation at the unit boundary; actual next-turn continuation requires the separate real Pi/browser observation. Alternatively use a supported acknowledgement API after demonstrating its lifecycle behavior; do not patch Pi or assume an undocumented promise.

Required checks: a fake void bridge that returns normally and reports a later failure must not be represented as confirmed turn delivery; duplicate accepted requests still invoke the bridge once. Record a real same-session next-turn separately from a local 202.

## Initial finding P1-02 (resolved by design amendment): In-flight render has no originating-epoch admission contract

Lazy HTTP startup is asynchronous. Checking cancellation immediately before commit does not prove that a render started on one branch/session cannot complete startup after navigation, reset, shutdown, or disable/re-enable and then publish old UI into the new context. The spec isolates browser actions by epoch but does not give pending render work the equivalent authority check. The technical trace and tests cover cancellation and restoration, not this crossing.

Required amendment: capture a render operation's epoch/lifecycle generation at tool entry, before any await, and require that authority to still match immediately before commit. Reset/navigation/shutdown must invalidate pending work even if the supplied AbortSignal is not aborted. If disable/re-enable is meant to invalidate pending renders, use a separate operation generation or explicitly document the desired behavior. Server startup completion must not resurrect a closed extension instance. Commit and publication remain one synchronous operation after these checks.

Required checks: hold lazy startup pending, begin a render on A, reset/restore to B (and separately close), release startup, and assert no old surface/revision is committed and no successful tool result is returned. Verify a fresh render on the current generation still works. Include the case in AC-02/AC-06/AC-07 mapping and technical trace.

## API feasibility and implementation obligations

The pinned npm artifacts were independently fetched and inspected from the registry (not inferred from illustrative documentation): `@a2ui/agent@0.1.0`, `@a2ui/web_core@0.15.0`, and `@a2ui/lit@0.15.0`. Extracted inspection copies are under `/tmp/pi-a2ui-design-review/`. The architecture is feasible subject to executable characterization and the above amendments.

- The agent root exports `A2uiGenerator`, `ExpressFormatFactory`, `RendererState`, `CatalogConfig`, and component/function pruning transformers. A fresh `RendererState` supports synchronous transactions and explicit topology checks; complete-state materialization must still check a nonempty root because an empty surface can pass the SDK topology method.
- The Lit root exports the surface/controller, not a `basicCatalog` export. For protocol 1.0, `@a2ui/web_core/catalogs/basic/v1` supplies the official implementation-backed catalog. Its components pair official universal element classes with versioned APIs via `toWebComponentImplementation`; a catalog reconstructed only from schema JSON has no rendering implementation. Record the exact compiler and browser catalog construction in the spec. Match catalog IDs and six allowed components, and explicitly prune **all functions** on both sides; component pruning alone retains functions. Prove actual DOM rendering and button/TextField behavior, not just JSON compilation.
- Official Text `body` requests a markdown renderer but safely displays escaped literal text when none is configured. For this plain-text MVP, omit the optional markdown package/registration and verify literal `<img>`, links, and HTML remain text and create no requests. Do not solve peer conflicts with forced dependency installation.
- The schemas allow action `userMessage`, context bindings, and function-shaped values. The post-compilation allowlist must recursively reject calls/system expressions and preserve only declared event context. Bound context type inference must be deterministic (for example reachable TextField value bindings are strings, including number-style inputs); unspecified paths/types must be rejected rather than guessed. Test literal tampering, extra keys, missing keys and wrong types independently from stale revisions.
- Current snapshots plus non-evicting bounded event IDs are reasonable for process-local duplicate suppression. This is not crash-proof delivery. Clone/freeze validated messages so a caller or SSE subscriber cannot mutate committed state after validation. Materialize/restore complete state without running actions or functions.
- Loopback binding, exact Host/Origin, fragment bootstrap, HttpOnly SameSite cookie, no CORS, restrictive CSP, body/client/queue limits, and shutdown ownership provide a coherent local boundary. Cookies cannot literally be scoped to a TCP port; use a unique process/port cookie name and per-process random value, validate it only on the matching service, and document trusted-local-process scope. SSE may legitimately omit Origin, so require exact Host and authentication there and reject a present foreign Origin. Test cross-instance credentials and connection cleanup.
- Make depth limits explicit (tree/data/source structure as applicable) or name verified pinned SDK limits; “depth limits” without a value or source is not an executable acceptance criterion. Snapshot/component byte/count limits must be checked before committing/restoring, and rejected listeners/slow clients must not turn a completed commit into a tool error with inconsistent persistence.

## Re-review resolution and GO

Re-read the amended canonical spec, rounds 1–3, implementation plan, and `docs/checks/002-sdk-characterization.md` on 2026-11-13. The characterization is author-provided executable API evidence; this reviewer independently inspected registry artifacts and Pi source, but did not independently run the author's characterization or claim browser/runtime success.

- **P1-01 resolved at design level:** spec and AC-03 now separate a single local void bridge invocation from Pi queue/turn/model success; 202 and Sent to Pi have that meaning. Async failure remains Pi-owned, the unit oracle checks one invocation, explicit no-template expansion is required, and real continuation remains separately observed acceptance.
- **P1-02 resolved at design level:** originating epoch is captured before any await; commit checks current authority and shutdown, late startup closes, disable invalidates pending work with an operation generation. AC-02/AC-06 and plan require deferred-startup reset/close/disable regressions. Current-epoch work can proceed afterward.
