## Admission decision

No P0/P1 design blocker identified. The scoped design closes the requested path: Pi-supplied static coding records → SDK-derived Express compiler/schema validation → bounded per-epoch immutable-ID admission → atomic snapshot/revision → local escaped browser implementation → existing declared Button event with exact current literal record IDs → existing Pi follow-up. It adds no file mutation, shell, HTML evaluation or RPC authority.

The versioned Pi catalog ID and restricted Basic ID are explicitly separated. Shared schema-only API entries and browser implementations must emit equal catalog JSON; custom types cannot be restored under Basic merely because the current catalog knows them. Keeping snapshot version1 is coherent because catalog IDs carry component capability and each restore still validates the complete surface.

The identity ledger stores bounded hashes, retains at most256 identities per epoch, permits unchanged-ID/unchanged-record reuse, rejects changed payload and conflicting restore, and reconstructs only the current restored records under a new epoch. The plan explicitly tests failed admission preserving both published state and ledger; this is essential to prevent a failed overbudget render from consuming or poisoning identity authority.

TestResults is clearly described as Pi-supplied structured evidence. Exact count validation detects internal inconsistency; it does not certify that a command ran. Labeling provenance in the renderer and requiring actual executed test records in installed/live acceptance preserves this distinction. CodeDiff promises an exact before→after transformation and linear bounded contiguous block, without implying a minimal edit script.

## TDD/final-review expectations

C-01–C-06 map to concrete deterministic/native/browser/live checks in the walkthrough. Implementation review should challenge these counterexamples within that existing contract:

- Diff reconstruction for empty string, final newline, CRLF, unicode and repeated lines; collect unchanged+removed/added pieces and reconstruct both exact original strings. Do not infer correctness from colored line counts alone.
- Atomic identity admission when adding two records crosses capacity, when a byte/component budget fails after a new identity is computed, and when restoring two conflicting current records. Record hashing must be deterministic over the validated immutable data, including provenance and summaries.
- A previous ID's data cannot be reassigned through another surface; replacing a surface must invalidate its old Button revision even when ID text is reused. Literal record IDs cannot be substituted with input bindings or a different result/proposal.
- Basic catalog restore must reject CodeDiff/TestResults; current catalog must retain the reviewed v0.1.1 form contracts and shared legacy TextFields. Browser/schema parity must inspect all advertised types and actual mounting, not only matching component-name counts.
- Static schema limits and inherited source/snapshot/JSON/tree limits apply together; executable chart-like options, injected source text and fabricated summaries are rejected or rendered literally according to the specified data role.
- Actual C-06 acceptance executes a deterministic test, derives its recorded outcome/counts from that execution, renders those records through a production-only installed package and verifies the same-conversation model acknowledgement of the exact reviewed record IDs. Displayed “pass” text alone is insufficient.

These are implementation/verification obligations, not claims that they have already passed.
