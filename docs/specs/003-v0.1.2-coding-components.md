## User outcome and scope

Users can inspect a proposed code change and structured test results without reconstructing them from prose, then return an explicit choice to Pi.

IN: read-only CodeDiff with named file/revision and before/after or normalized patch data; TestResults with case IDs, status, summary and bounded failure details; a versioned Pi catalog with shared schemas and browser implementations; named follow-up events referencing committed result IDs.

OUT: browser file editing or direct writes, IDE/editor replacement, automatic patch application, shell execution in widgets, arbitrary HTML, live logs/charts, and remote hosting. Existing form/layout components continue to work.

## User stories and acceptance criteria

| ID | Story / Given-When-Then acceptance |
| --- | --- |
| C-01 | Given a named proposed file revision, when CodeDiff renders additions/deletions/unchanged/empty/unicode content, then the displayed change corresponds to that exact proposal and all source remains literal escaped content. |
| C-02 | Given recorded test cases, when TestResults renders pass/fail/skip/error and details, then displayed counts/status match the supplied structured records; duplicate IDs and inconsistent summaries reject. |
| C-03 | Given a committed proposal/result, when a user selects a follow-up action, then only its current immutable ID/revision and permitted event/context reach Pi; the widget itself never writes a file or runs a command. |

| C-05 | Given0.1.0/0.1.1 or new coding snapshots, when restoring/upgrading, then the declared compatibility policy is honored; stale/oversized/incompatible proposals do not execute or silently become current. |
| C-06 | Given built0.1.2 and glm-5.3-flash, when a code-review/test-summary UI is generated and a choice submitted, then the real next Pi reply refers to the correct reviewed proposal/result. |

## Technical design and test intent

Define a new versioned Pi catalog ID instead of adding custom types under the official Basic Catalog ID. Share property/event schemas and prompt instructions; load schema-only catalog definitions on the server and pair them with local Lit/Web Component implementations in the browser. Extend compile/restore/action validation with explicit coding contracts. Use SDK catalog-derived Express signatures; do not create a second DSL or executable model-generated UI.

Keep CodeDiff read-only; use an existing Button event for the first follow-up path where possible, with a literal current proposal ID. TestResults data is supplied/derived from actual tool evidence; do not invent a pass from displayed text. Preserve total snapshot/resource budgets; reject large proposals with an actionable message rather than truncating into a misleading change.

Map C-01/02 to deterministic renderer/structured-record tests and adversarial content cases; C-03/05 to revision/authority/restore rejection tests; C-04 to shared-schema parity and actual-browser mounting; C-06 to an installed-package/GLM round trip. Include real empty/new/deleted files, source HTML/script-like strings, mixed case outcomes and a stale proposal action.

## Risk and rollback

The primary risks are misleading diff/test evidence, unsafe content rendering and broadening UI execution authority. Pin data to a named proposal/tool-result revision and keep execution in Pi's normal permissions. Version the catalog and define compatibility before implementation. Roll back to0.1.1 by switching package registration; no direct filesystem action or data migration follows from a browser click.

## Concrete contract (2026-11-13)

New catalog ID: https://jackallink.github.io/pi-a2ui/catalogs/coding-v1.json (identifier only, never fetched). New rendering uses this catalog. Restore accepts that ID and the restricted official Basic ID; custom types are never accepted under Basic. Snapshot remains version1. Shared schema-only APIs live separately from browser Web Component implementations; parity checks compare their emitted catalog JSON.

CodeDiff static properties: proposalId (1–64 safe ID), filename (nonempty bounded literal), baseRevision (nonempty bounded literal), before/after (each <=16KiB, <=512 lines). It displays a linear-time contiguous change block: common prefix/suffix are unchanged, middle old lines removed and new lines added. It is an exact before→after transformation, without a minimal-diff claim. No truncation, arbitrary HTML, editing or filesystem access. Empty/new/deleted/unicode source is supported.

TestResults static properties: resultId (safe ID), command and evidence (nonempty bounded literal provenance text), cases (<=128 records {id,name,status,details?}, status pass/fail/skip/error), summary (exact counts of those four statuses). Duplicate case IDs and inconsistent counts reject. This displays Pi-supplied structured evidence; the browser does not certify a test execution. The renderer explicitly labels provenance as reported by Pi. Actual live acceptance must supply records from a real executed test, not invented passing prose.

Each surface admits at most one CodeDiff and one TestResults. Every follow-up Button on that surface declares literal proposalId/resultId matching those records (both when both present). The existing exact literal/epoch/revision/source checks enforce submission. IDs are immutable within an epoch: the same ID with different record data rejects atomically across replacements/surfaces; up to256 identities are retained using bounded hashes, reset only on new session epoch. Restoring rebuilds this ledger from the restored current records and rejects conflicting IDs. Full source/records remain subject to source/snapshot/collection budgets.
