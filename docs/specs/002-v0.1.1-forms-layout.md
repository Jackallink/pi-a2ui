## User outcome and scope

Users can express booleans, choices, bounded numbers and dates without encoding every answer as text, and navigate related panels in tabs.

IN: official CheckBox, ChoicePicker, Slider, DateTimeInput, Tabs and Divider; existing six components remain available. Single/multiple ChoicePicker values follow the SDK's string-array contract. CheckBox uses boolean, Slider finite number/range, date/time canonical strings. Adapt component slots including Tabs tabs[].child, matching model instructions and typed action-context validation.

OUT: custom coding components, media, List/Modal, arbitrary functions/checks, remote access, live logs/charts and new execution permissions.

## User stories and acceptance criteria

| ID | Story / Given-When-Then acceptance |
| --- | --- |
| F-01 | Given a rendered checkbox and slider with initialized bindings, when edited and submitted, then Pi receives the actual boolean and finite bounded numeric values. |
| F-02 | Given declared single/multiple choice options, when selected and submitted, then only permitted option IDs in the SDK string-array shape are accepted; unknown IDs, duplicates or invalid selection counts are rejected without dispatch. |
| F-03 | Given date/time configuration, when a value is submitted, then its format and declared min/max constraints are checked; invalid values preserve the prior accepted state. |
| F-04 | Given nested tabs and dividers, when switching tabs or updating another surface, then child references remain valid and unrelated draft input is preserved. |
| F-05 | Given restored old0.1.0 snapshots or new typed snapshots, when loading a branch, then compatible state restores without coercion; wrong types, bad slots, stale revisions and over-budget input reject atomically. |
| F-06 | Given the built0.1.1 package and Agent Plan glm-5.3-flash, when a mixed-type requirement form is generated/submitted, then the actual next Pi model reply reflects the submitted values and reload releases resources. |

## Technical design and test intent

Update src/catalog.ts, src/compiler.ts and src/session.ts together: each admitted input has a declared binding type, initial-value validator and submitted-value validator. Inspect typed SDK bindings rather than assuming TextField strings. Keep button/event authority. Extend tree validation from child/children to declared slots, preserving depth/unique-parent budgets. Update extension.ts instructions and browser integration only where the SDK contract requires it; reuse official widget implementations.

Map F-01/02/03 to focused session/compiler tests with literal typed oracles and zero-dispatch rejection cases; F-04/05 to native snapshot and real-browser navigation/restoration tests; F-06 to installed-package/GLM acceptance. Required regression examples: forged selection ID; array submitted for boolean; NaN/infinite/out-of-range slider; invalid calendar date; missing tab child; unsupported legacy snapshot. Each behavior starts with a meaningful failing test.

## Risk, compatibility and rollback

Typed values widen a formerly string-only authority boundary; retain exact context keys and permitted literal values. Snapshot/catalog changes need an explicit old-version compatibility decision before coding. Prefer capability/schema-derived handling over independent UI allowlists. Rollback uses the unchanged v0.1.0 artifact and version-specific package registration; no session/credential migration is authorized implicitly.

## Concrete contract (2026-11-13 takeover)

Keep Basic Catalog ID and snapshot version1; accept v0.1.0 saved surfaces through the same strengthened validator, with no coercion. Each new typed input value binding has a unique absolute path and cannot collide with TextField; multiple legacy TextFields may share an absolute string path; context must reference that exact reachable input. Static input values are validated too. Slider min/max/steps and ChoicePicker options/variant are static authority. Duplicate option IDs reject; single choice allows zero or one item. Slider steps denotes divisions, with a floating point tolerance for on-grid values. Date/time flags are explicit, at least one true; values use local calendar YYYY-MM-DD, HH:mm or YYYY-MM-DDTHH:mm, allowing optional :00 seconds. Empty input is allowed. Calendar validity and matching static min/max are enforced; timezone strings and dynamic bounds reject rather than silently normalize.

Tabs traversal includes every tabs[].child with existing unique-parent/depth bounds. Official tab widgets may remount a panel; bound drafts survive in the persistent SDK data model. No new renderer or transport is required.
