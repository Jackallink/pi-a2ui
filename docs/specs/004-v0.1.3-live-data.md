# 0.1.3 — Live logs and charts

Lifecycle: review-ready. Profile: strict. Scope approved for iteration planning on2026-11-13; walkthrough-approved → tdd-approved → in-progress after independent design GO (docs/checks/v0.1.3-design-review.md). Dependency:0.1.2.

## User outcome and scope

Users can follow bounded tool output and inspect structured result trends while retaining control of the same Pi task.

IN: LogView fed by Pi tool execution/output events, bounded incremental updates, sequence/gap handling and snapshot recovery; a Chart component for basic line/bar series with a constrained data schema; preserved browser scroll/selection where appropriate; paused/disconnected/error/end states.

OUT: remote telemetry services, unlimited log retention, terminal emulation or commands executed from log text, arbitrary chart JavaScript/options callbacks, new model calls per log chunk, automatic operational remediation or remote hosting.

## User stories and acceptance criteria

| ID | Story / Given-When-Then acceptance |
| --- | --- |
| L-01 | Given an authorized current-session tool stream, when output arrives, then LogView receives ordered bounded updates without an extra model call per chunk. |
| L-02 | Given logs exceed1000 lines or64KiB per view, when appended, then the older portion is bounded and the UI visibly indicates omitted earlier content; total snapshot remains within256KiB. |
| L-03 | Given a paused/slow/disconnected client or sequence gap, when updates resume, then it recovers a coherent bounded snapshot; memory/queues stay bounded and scroll behavior is deterministic. |
| L-04 | Given line/bar chart data, when rendered/updated, then finite points/labels and series mapping match input; reject over4 series, over200 points per series, malformed/nonfinite values and executable options. |
| L-05 | Given cancellation, tool end, session/tree change, reload or exit, when lifecycle changes, then old streams cannot update the new session and subscriptions/timers/listeners are released. |
| L-06 | Given another surface with unsent input, when log/chart data changes at up to10 published batches/second, then input, action authority and structural component identity remain coherent. |
| L-07 | Given built0.1.3 and glm-5.3-flash, when Pi opens an execution canvas and tools emit real output, then browser progress/end/results are observed and a selected next action returns to the same conversation. |

## Technical design and test intent

Add explicit data updates to the current atomic-layout session model. Distinguish structural revision/action admission from live data sequence; document exactly when actions become stale. Use deterministic tool-event collection and a bounded ring buffer/coalescing path. The recovered LogView payload uses bounded text rather than a1000-element JSON collection; chart series are capped at200 points each, below the inherited256-entry collection limit. Aggregate4096-node/256KiB snapshot limits still apply. The model defines the layout and interprets results rather than regenerating a surface for every log line. Unsubscribe by owning tool/session lifecycle.

Keep SSE/POST transport and existing authentication boundary. Snapshot recovery is authoritative after gaps; never turn missed log chunks into unbounded server history. Chart rendering uses local packaged code and a constrained series/axis/data contract, without evaluating model-supplied script or fetching arbitrary resources.

Map L-01/02 to native event/buffer tests with independent order/truncation oracles; L-03/05 to reconnect/backpressure/cancel/cleanup tests; L-04 to chart schema and actual renderer tests; L-06 to concurrent input/data/revision browser cases; L-07 to real Pi/tool/browser/GLM acceptance. Include split/unicode chunks, duplicate/out-of-order notification, silent/failed tools, initial empty chart and a client that stops reading.

## Risk and rollback

Incremental data crosses lifecycle/resource boundaries; require strict review before code. Current published snapshot/client/action limits remain binding unless a reviewed spec explicitly changes them. Proposed line/point/rate limits above are iteration acceptance targets, not0.1.0 capabilities. Rollback stops subscriptions and returns to the0.1.2 package; it does not delete Pi history or require credential changes.

## Concrete contract (2026-11-13)

New live-v1 catalog identity under the Pi catalog URL; restore also accepts coding-v1 and restricted Basic. LogView(stream="tools") has server-controlled text/omitted/state defaults; at most one per surface. It receives literal text from current-run native Pi tool start/update/end, excluding a2ui_* tools. Pi1.5 bash update content is a cumulative output snapshot; duplicate/stale prefixes are ignored and changed/truncated snapshots are visibly marked. Support32 active tool identities, each last snapshot <=64KiB, and a bounded aggregate ring. Unknown/end-of-run/session-old IDs cannot append. Collection starts only after native agent_start, ends on agent_end; branch/session changes, pause/reload/shutdown invalidate it and clear timers. No model request is made by collection.

Log ring is at most1000 lines and64KiB JSON-encoded text (also <=64KiB UTF8), with a visible omitted flag. Across multiple views divide a64KiB serialized log budget; structural admission reserves that plus1024 bytes under the inherited256KiB snapshot budget. Malformed/over-budget updates reject atomically. LogView has a local pause/resume display button; paused text/selection remains stable while the bounded latest buffer advances. Auto-follow only when previously at bottom; otherwise retain numeric scroll position. Connection state remains visible in the existing canvas header.

Chart(kind=line|bar,series=[{name,points:[{label,value}]}]) uses <=4 uniquely named series and <=200 finite points per series, labels <=128 chars. Series align by identical label arrays (including order). Native local SVG plus an accessible value table; negative/zero/empty/large finite values handled without executable options or remote resources. A new a2ui_update_chart(surfaceId,revision,componentId,series) tool updates only an existing current Chart's series, preserves kind/layout/inputs, returns bounded snapshot details, and uses the same Pi permissions. Chart data may be supplied from actual tool results; no per-log-chunk model call.

Live components update through existing SDK updateComponents, never full layout replacement. SurfaceRecord gains optional dataSequence (legacy absent=0), independent of structural revision; button authority remains epoch+structural revision. State mutation is bounded/atomic, SSE data batches coalesce globally at most10 batches/sec with latest per-surface live component payloads. Batch {epoch,surfaces:[{surfaceId,revision,sequence,components}]} increments sequence once per published batch/surface. Queues hold at most4 surfaces; timers/listeners are released on reset/close. Structural replacement drops that surface's queued patch.

Client ignores duplicate/old sequence and wrong epoch/revision, applies only existing LogView/Chart IDs, and reconnects SSE on gaps to receive an authoritative bounded snapshot before continuing. It ignores queued events from a superseded EventSource. A same-revision snapshot applies only live component data and never remounts form/layout nodes. Restored running logs become interrupted; live tool events are never replayed from history. Successful chart tool snapshots join a2ui_render as authorized restoration records.

### Admission refinements from independent counterexamples
All live-component snapshots (including Chart-only) reserve1024 bytes for counter/lifecycle growth. Restore enforces the64KiB aggregate encoded log budget and equal per-view shares, not merely each view's64KiB maximum. Adding another view when existing text exceeds its new share rejects atomically; replace/clear the existing view first. Tool cumulative windows retain64KiB independently of the ring's1000-line bound; shorter unversioned cumulative snapshots are stale. Pi truncation metadata totalBytes is monotonic evidence for fresh rolling windows; lower/equal counters are ignored (terminal formatting may differ). Fresh changed windows are visibly marked.

Logical string length alone does not prove bounded retained memory: log/window truncation must materialize bounded storage rather than retain arbitrary V8 source backing. A Node24 expose-gc regression checks a32MiB transient input releases its backing after collection.
